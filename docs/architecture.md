# Архитектура
## Данные

| Система | Что | Почему |
|---|---|---|
| PostgreSQL | Справочники | Имитирует продуктовую базу сервиса объявлений: нормализованные таблицы, внешние ключи, мало строк, частые обновления |
| ClickHouse | Поведенческие события | Сотни миллионов строк, запись батчами, запросы - агрегаты по периоду. Колоночное хранение и разреженный индекс |
| Vertica | Финансы | Корпоративное DWH: заказы, деньги, точные расчеты, проекции под разные паттерны чтения |
| Trino | Джойны между системами | Один SQL поверх трех источников без копирования данных; используется для расчетов раз в сутки и сверок, а не под каждым дашбордом |
| Redash | Дашборды | BI-инструмент команды: параметры, расписания, алерты, сниппеты |

## Слои и правила

* **raw** - данные как пришли, включая повторные доставки. Дашборды сюда не ходят
  (нарушения ловит BI Health).
* **staging** - `stg_events`: дедупликация через ReplacingMergeTree по ключу события
  и `OPTIMIZE FINAL` один раз при сборке.
* **marts** - витрины с явным зерном, описанные поколоночно в `dbt/models/schema.yml`.
  Тег `certified` - прошли тесты, есть владелец; только на них строятся официальные дашборды.
* **dq** - журнал проверок качества.
* **MV-агрегаты** (`listing_daily_agg`, `users_daily_agg`) - оперативные, считают сырой поток
  вместе с дублями; для сертифицированных цифр используются витрины dbt.

## Ключевые решения

**Ключ сортировки `raw.events` - `(event_date, category_id, event_type, listing_id)`.**
Дашборды фильтруют по периоду и категории, воронка всегда делится по типу события.
Отдельно проверялась гипотеза, что для запросов "по объявлению" нужна проекция: замер
показал, что ключ и так отсекает больше 99% строк (подробно в `performance.md`).

**Дедупликация при сборке, а не при чтении.** `FINAL` или `LIMIT 1 BY` в каждом запросе
дашборда стоит в 3–4 раза дороже. Сборка stg_events платит один раз.

**Инкремент `fct_listing_daily` - `insert_overwrite` по месячным партициям.** Пересчитываются
партиции, куда попадают последние `lookback_days` дней, и подменяются атомарно через
`REPLACE PARTITION`. Мутации (`DELETE`) в ClickHouse дорогие, delete+insert не нужен.
Подводный камень, пойманный сверками: если перегенерировать сырые данные целиком и запустить
dbt без `--full-refresh`, старые партиции витрины останутся от прошлых данных, и проверка
`stg_vs_mart_views` упадет. Поэтому `make dbt` всегда делает полную пересборку.

**Федеративный запрос не под дашбордом.** Trino раз в сутки считает эффект заказов
по трем системам и вставляет результат в ClickHouse (`marts.promo_order_effect`).
Дашборд читает готовую таблицу за миллисекунды и не зависит от доступности Vertica.
Таблица создается заранее в ClickHouse с не-Nullable типами: CTAS из Trino сделал бы колонки
Nullable, а ключ сортировки MergeTree на Nullable-колонках не работает.

**Словари ClickHouse для названий.** `dictGet('marts.dict_categories', 'name', category_id)`
вместо джойна: справочник живет в PostgreSQL, ClickHouse перечитывает его раз в 5–10 минут.

**Две ступени отбраковки в Vertica.** `COPY … REJECTED DATA` ловит технический брак (строка
не парсится), SQL-валидация - бизнес-брак (нет продавца, отрицательная сумма) с причиной
в карантине. Плохие строки не теряются молча и не попадают в выручку.

## Нюансы движков, которые встретились по ходу

* Trino по умолчанию видит `String` из ClickHouse как `varbinary`: сравнение со строкой
  не работает, пока в каталоге не включен `clickhouse.map-string-as-varchar=true`.
* Trino не читает колонки `AggregateFunction`, поэтому для федерации нужны витрины
  с обычными типами.
* В ClickHouse псевдоним, совпадающий с именем колонки внутри агрегата
  (`sum(views) AS views`, затем `sum(contacts) / sum(views)`), дает ошибку
  "aggregate inside aggregate" - в запросах дашбордов метрики названы `views_total` и т.п.
* Скетч `uniq` тяжелый: агрегат и uniq-состоянием на каждой строке "объявление b день"
  считает аудиторию за месяц медленнее, чем точный подсчет по сырым событиям.
  Помогает грубое зерно и компактный `uniqHLL12`.
* Метаданные Redash: просмотр дашборда через API тоже пишется как событие `view`,
  поэтому порог "кандидат на архивацию" - меньше 5 просмотров за 30 дней, а не ноль.
